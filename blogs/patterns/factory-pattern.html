Understanding the Factory Method Design Pattern in .NET: A Simple 15-Minute Guide

Decoupling client code from concrete object creation. Learn how to dynamically instantiate strategy handlers and notification services based on configuration without tight coupling.

December 2025 • Design Patterns • 15 min read
#design-patterns #factory-method #csharp #dotnet #solid-principles

1. What Is the Factory Method Pattern?

The Factory Method Pattern is a creational design pattern that defines an interface for creating an object in a superclass, but allows subclasses to alter the type of objects that will be created.

In simple words: Instead of creating objects directly using the new keyword inside your business logic, you ask a dedicated Factory method to create the object for you.

💡 Real-World Analogy

Think of ordering food at a restaurant. As a customer (Client Code), you ask the waiter for a "Pizza" or "Burger". You don't go into the kitchen, buy raw flour, turn on the oven, and bake it yourself using new Pizza(). The kitchen (Factory) creates the dish and hands it back to you!

2. The Problem: Tight Coupling & Switch Bloat

Suppose you are building a system that sends user notifications via Email, SMS, and Push Notifications. Without the Factory Method, developers often write giant if/else or switch/case statements directly inside controllers:

// ❌ BAD: Tight Coupling & Violated Open/Closed Principle!
public class NotificationController : ControllerBase
{
    public async Task<IActionResult> SendNotification(string channelType, string message)
    {
        INotification notification;

        if (channelType == "Email")
        {
            notification = new EmailNotification("smtp.mail.com", 587);
        }
        else if (channelType == "SMS")
        {
            notification = new SmsNotification("SMS_GATEWAY_KEY");
        }
        else if (channelType == "Push")
        {
            notification = new PushNotification("FIREBASE_SERVER_KEY");
        }
        else
        {
            throw new NotSupportedException("Notification channel not supported.");
        }

        await notification.SendAsync(message);
        return Ok("Sent successfully!");
    }
}

Why is this approach dangerous? Every time your company adds a 4th channel (like WhatsApp), you MUST open and edit NotificationController. This violates the Open/Closed Principle (OCP) and leads to huge, fragile controller classes.

3. The Factory Method Solution in C#

Let's refactor this cleanly into 4 simple, step-by-step components with clear explanations for each step.

Step 1: Define Product Interface (`INotification`)

Explanation: Before creating specific notification channels (Email, SMS, Push), we first define an abstraction interface. This interface forces all concrete notification types to follow a unified contract (having a ChannelName property and a SendAsync method). This ensures that client code can work with ANY notification type polymorphically without knowing the underlying implementation details!

public interface INotification
{
    string ChannelName { get; }
    Task SendAsync(string message);
}

Step 2: Implement Concrete Products (`EmailNotification`, `SmsNotification`)

Explanation: Next, we implement the INotification interface in concrete classes. Each concrete class contains the channel-specific delivery logic (e.g., SMTP settings for Email, HTTP API payload for SMS). Because they both implement INotification, they can be used interchangeably by the factory without breaking client code.

public class EmailNotification : INotification
{
    public string ChannelName => "Email Channel";

    public async Task SendAsync(string message)
    {
        // Channel-specific logic (e.g. SMTP client call)
        Console.WriteLine($"[EMAIL] Sending email message: {message}");
        await Task.CompletedTask;
    }
}

public class SmsNotification : INotification
{
    public string ChannelName => "SMS Channel";

    public async Task SendAsync(string message)
    {
        // Channel-specific logic (e.g. SMS Gateway API HTTP request)
        Console.WriteLine($"[SMS] Sending SMS message: {message}");
        await Task.CompletedTask;
    }
}

Step 3: Define Abstract Creator (`NotificationFactory`)

Explanation: The Creator class declares the abstract CreateNotification() Factory Method. Notice that NotificationFactory can also contain core business workflows (like logging, retry mechanisms, or auditing) in DeliverNotificationAsync() that rely on the product created by the Factory Method!

public abstract class NotificationFactory
{
    // 🔑 The Factory Method declared here!
    public abstract INotification CreateNotification();

    // High-level template workflow relying on the created product
    public async Task DeliverNotificationAsync(string message)
    {
        // Call the factory method to get a product
        var notification = CreateNotification();
        Console.WriteLine($"[FACTORY] Dispatching via {notification.ChannelName}");
        await notification.SendAsync(message);
    }
}

Step 4: Implement Concrete Factory Subclasses (`EmailNotificationFactory`, `SmsNotificationFactory`)

Explanation: Finally, we create concrete factory subclasses that override CreateNotification() to instantiate specific products. When client code calls EmailNotificationFactory.CreateNotification(), it gets back an EmailNotification instance cast as INotification!

public class EmailNotificationFactory : NotificationFactory
{
    public override INotification CreateNotification() => new EmailNotification();
}

public class SmsNotificationFactory : NotificationFactory
{
    public override INotification CreateNotification() => new SmsNotification();
}

4. Integrating with ASP.NET Core Dependency Injection

You can register factories cleanly in Program.cs and resolve them dynamically without hardcoding:

// Program.cs
builder.Services.AddTransient<EmailNotificationFactory>();
builder.Services.AddTransient<SmsNotificationFactory>();

// Controller
public class NotificationController : ControllerBase
{
    private readonly EmailNotificationFactory _emailFactory;

    public NotificationController(EmailNotificationFactory emailFactory)
    {
        _emailFactory = emailFactory;
    }

    [HttpPost("email")]
    public async Task<IActionResult> SendEmail([FromBody] string text)
    {
        await _emailFactory.DeliverNotificationAsync(text);
        return Ok();
    }
}

5. Key Benefits & When to Use

Benefit Why It Matters in Enterprise Software
Loose Coupling Client code does not care which concrete class gets created, only that it satisfies the interface.
Open/Closed Principle You can introduce new product types into the application without breaking existing client code.
Single Responsibility Object creation logic is isolated in one place, making unit testing far easier with mock objects.

6. Conclusion

The Factory Method pattern is an essential building block in modern .NET development. By separating object creation from execution, your code becomes modular, extensible, and ready for enterprise scale.
